# Combat Core — Task 01

`src/combat-core/index.ts` — независимое от Phaser, React, DOM и хранилища ядро расчётов и состояния. Один `CombatCore` владеет сущностями одной боевой сессии. Игровой цикл прототипа пока не подключён к этому модулю.

## Публичный API

```ts
import { calculateCharacterStats } from '../src/character-stats';
import { CombatCore } from '../src/combat-core';

const core = new CombatCore(() => 0.99); // Для игры можно передать свой RNG или использовать Math.random по умолчанию.
core.addEntity({
  id: 'hero',
  affiliation: 'player',
  stats: calculateCharacterStats('mage', 50).combatAttributes,
});
core.addEntity({
  id: 'enemy-1',
  affiliation: 'enemy',
  stats: calculateCharacterStats('warrior', 50).combatAttributes,
});

const attack = core.createAttack({
  attackerId: 'hero',
  damageType: 'magical',
  coefficient: 1,
});
const result = core.resolveAttack(attack, 'enemy-1');
// attack.baseDamage = 1260; attack.critical = false;
// RES 300 => result.damage = 315; HP 1600 => 1285.
for (const event of result.events) {
  // Передать event будущему адаптеру игры. Ядро не вызывает рендерер или callback.
}
```

| Интерфейс/операция                                 | Контракт                                                                                                                                                             |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CombatEntityStats`                                | `Pick<CombatAttributes, ...>`: Max HP, физический/магический урон, Resistance, Crit Chance/Damage, Dodge Chance. Принимает и полный существующий `CombatAttributes`. |
| `CombatEntityInput`                                | Уникальный в сессии `id`, `affiliation: 'player' \| 'enemy'`, `stats`, необязательный `currentHp` (по умолчанию Max HP).                                             |
| `CombatEntity`                                     | Неизменяемый снимок: статистика выше, `id`, `affiliation`, `currentHp`, `alive`. `alive` выводится из HP и не задаётся вызывающим кодом.                             |
| `CombatCore.addEntity(input)`                      | Регистрирует сущность. Повторный ID запрещён, в том числе после смерти первой сущности.                                                                              |
| `CombatCore.getEntity(id)`                         | Текущий immutable snapshot; старые полученные снимки не изменяются. Неизвестный ID — ошибка.                                                                         |
| `CombatCore.createAttack(AttackRequest)`           | Создаёт неизменяемый `AttackSnapshot`. Мёртвый источник не может инициировать атаку.                                                                                 |
| `CombatCore.resolveAttack(snapshot, targetId)`     | Разрешает попадание в одну цель; возвращает `DamageResult` с исходом, HP и событиями.                                                                                |
| `CombatCore.heal(id, amount)`                      | Возвращает `HealingResult`, фактическое восстановление и событие при положительном восстановлении. Мёртвый остаётся мёртвым.                                         |
| `CombatCore.changeMaxHp(id, delta)`                | Меняет Max HP и Current HP на тот же delta, с оговорённым сохранением жизни. Возвращает `EntityChangeResult`.                                                        |
| `CombatCore.updateEntityStats(id, stats)`          | Заменяет полный набор объединённых характеристик. Для Max HP применяет ту же delta-политику. Не реализует правила сложения бонусов.                                  |
| `calculateSuccessfulDamage(rawDamage, resistance)` | Чистый расчёт сопротивления и финального округления с минимумом 1 для положительного raw damage.                                                                     |
| `RandomSource`                                     | Функция `() => number`, каждый результат должен быть конечным и в `[0, 1)`.                                                                                          |

`AttackRequest` содержит `attackerId`, `damageType: 'physical' | 'magical'`, `coefficient`. В `AttackSnapshot` также находятся последовательный ID (`attack-1`, уникальный внутри экземпляра ядра), `baseDamage`, `critical` и `rawDamage`. Все поля — значения; ссылки на изменяющегося атакующего нет. Источник, его характеристики и коэффициент проверяются при создании. На разрешении проверяются поля снимка, в том числе при передаче сериализованных данных; это проверка формы и допустимых чисел, не механизм защиты от подделки в однопользовательской игре.

## Порядок разрешения урона

**Один раз при инициации атаки:**

1. Найти живого атакующего; проверить тип урона и конечный неотрицательный коэффициент.
2. Выбрать `physicalDamage` или `magicalDamage`, вычислить `baseDamage = stat * coefficient`.
3. Сделать один RNG draw и сравнить `roll < criticalChance / 100`.
4. Для крита вызвать существующий `calculateCriticalDamage(baseDamage, criticalDamage)`; иначе оставить базовый урон. Это `rawDamage` до защиты цели.
5. Зафиксировать снимок. Изменения атакующего влияют только на следующие атаки.

**Для каждой выбранной вызывающим модулем цели:**

1. Проверить снимок и существование цели.
2. Если цель мертва, вернуть `status: 'inactive'`, нулевой урон и пустые события; RNG не расходуется.
3. Сделать отдельный RNG draw для Dodge этой цели: `roll < dodgeChance / 100`. При успехе вернуть `status: 'dodged'`, нулевой урон и событие `dodge`.
4. Применить **текущий** Resistance цели через `applyResistance(rawDamage, resistance)` из Character Stats: `rawDamage * 100 / (100 + resistance)`.
5. При `rawDamage > 0` применить `Math.max(1, Math.round(mitigated))`. `Math.round` округляет положительное `.5` вверх. При `rawDamage === 0` урон остаётся нулевым.
6. `currentHp = Math.max(0, previousHp - damage)`. Фактическая потеря `appliedDamage = previousHp - currentHp` не превышает оставшиеся HP. Никакого переноса остатка в другую цель нет.
7. Сохранить состояние **до** возврата событий. При фактической потере HP вернуть `damage`; при переходе к 0 HP сразу после него вернуть единственный `death`.

Один и тот же `AttackSnapshot` передаётся всем целям — крит не пересчитывается. Уклонение и сопротивление проверяются отдельно по актуальным характеристикам каждой цели. `damage` — рассчитанный целочисленный урон; `appliedDamage` — реальная потеря HP с учётом overkill. Эти величины могут различаться.

Нулевой raw damage не наносит минимум 1 и не порождает `damage`/`death`. RNG-проверки всё равно имеют фиксированный контракт: один draw на создание атаки и один на каждую живую цель, включая нулевой шанс/урон. Значение RNG, равное границе вероятности, означает неуспех; шанс 0 не срабатывает даже при roll 0. Некорректный RNG вызывает ошибку, состояние HP остаётся прежним.

## HP и жизненный цикл

- HP и Max HP должны быть конечными; `0 <= currentHp <= maxHp`, `maxHp >= 1`. Минимальный Max HP 1 нужен для инварианта сохранения живой сущности хотя бы с 1 HP после уменьшения максимума. Изменения, нарушающие диапазон, отвергаются целиком.
- Healing — конечное неотрицательное число. Восстановление ограничено отсутствующими HP, Max HP не меняется. Мёртвым обычное лечение не помогает.
- При смене Max HP текущее HP сдвигается на ту же дельту; если дельта отрицательная и сущность была жива, итоговое HP не ниже 1. Рост Max HP не заполняет ранее потерянное здоровье сверх этой дельты.
- У мёртвого HP остаётся 0 при любом допустимом изменении Max HP/характеристик. Способа возрождения в API нет.
- После летального попадания `getEntity(id).alive` уже `false`. Дополнительный урон не производит повторный `death` и не расходует Dodge RNG.
- Инициализация с `currentHp: 0` означает уже мёртвую сущность и не создаёт искусственный переход смерти.
- Только успешный урон округляется. Дробные исходные HP, лечение и delta Max HP сохраняют точность; отдельное правило их округления в ТЗ не определено. При дробном остатке HP рассчитанный урон всё равно целочисленный, а фактическая потеря может быть дробной.

## События

`CombatEvent` — discriminated union: `DamageEvent`, `DodgeEvent`, `DeathEvent`, `HealingEvent`, `MaxHpChangedEvent`. Это замороженные объекты в замороженном массиве результата; состояние и сам результат также readonly/frozen.

- `damage`: attack/source/target IDs, тип, крит, рассчитанный и фактически применённый урон.
- `dodge`: attack/source/target IDs.
- `death`: entity/source/attack IDs. Генерируется только живой → мёртвый и ровно один раз.
- `healing`: ID и фактически восстановленная величина.
- `max-hp-changed`: ID, прежние/новые Max HP и Current HP. При delta 0 отсутствует.

Глобальной шины, подписок, очереди событий, зависимости от частоты кадров или callback из ядра нет. Вызывающий модуль потребляет каждый результат операции и передаёт события нужным системам. Повторное воспроизведение самим потребителем одного массива событий не является повторной эмиссией ядром. Порядок при летальном уроне — `damage`, затем `death`.

## Совместимость и валидация

Формулы и конфигурации Character Stats не менялись. Используются его `CombatAttributes`, `applyCombatAttributeCaps`, `applyResistance`, `calculateCriticalDamage`; новых формул характеристик и копий лимитов нет. На регистрации/обновлении принимаются уже объединённые значения и повторно применяется существующая идемпотентная граница caps. Resistance и Critical Damage не получают новых верхних лимитов.

Идентификатор — непустая строка, affiliation/type — строго заданные варианты. Все используемые характеристики и урон должны быть конечными неотрицательными числами. Валидация выполняется до записи состояния; переполнение промежуточного вычисления до Infinity вызывает ошибку вместо порчи HP или молчаливого ограничения характеристики. Новых зависимостей не добавлено.

Существующая `src/engine/systems/Combat.ts` продолжает обслуживать первый игровой прототип. Её поведение, Character Stats и UI этой задачей не заменены. `vitest.config.ts` включает обе группы тестов; `tsconfig.stats.json` проверяет оба независимых модуля и их тесты без DOM-типов. Команда `test:stats` сохраняет отдельный запуск Character Stats, `test:combat` запускает только Combat Core, а `npm test` — обе группы и прежние тесты прототипа.

## Открытые вопросы для интеграции

Эти механики не определены, поэтому ядро не вводит автоматические правила:

1. **Friendly fire и self-hit:** affiliation хранится, но фильтр допустимых целей должен быть утверждён будущей системой атак. `resolveAttack` применяет переданный снимок к переданной цели без такого фильтра.
2. **Повторное попадание:** ядро не ведёт hit-list для attack/target. Вызывающий модуль решает, сколько раз допустимо разрешать попадание; повторный вызов по живой цели — новая операция попадания с отдельным Dodge.
3. **Атака после смерти источника:** новая атака запрещена; существующий снимок не отменяется автоматически. Будущий модуль решает, продолжать ли разрешение уже выпущенных атак. Ядро не требует, чтобы источник был жив на момент разрешения.
4. **Отрицательный Resistance и другие отрицательные боевые статы:** правила debuff ниже нуля не заданы; текущий API отвергает такие входы. Формулы Character Stats при этом не изменялись. Перед поддержкой отрицательного Resistance нужен утверждённый числовой диапазон/правило.
5. **Целочисленность всех HP-операций:** ТЗ задаёт округление урона. Для лечения и изменения Max HP дополнительных правил округления не введено.

Poison/Burn/Bleed, periodic crit/dodge, revive, оружие, снаряды, движение, loot и XP не реализованы. Следующий рекомендуемый шаг — отдельно согласовать адаптер между системой атак и Combat Core: регистрация сущностей, создание одного снимка на атаку, разрешение по выбранным целям, потребление результатов HP/death. Эти интеграционные работы здесь не выполнялись.

```bash
npm run test:combat
npm run test:stats
npm test
npm run typecheck
npm run build
```

Vitest работает в Node. Тесты покрывают оба типа урона, Resistance, crit/dodge и вероятностные границы, минимум 1/ноль/округление, overkill, общие снимки на несколько целей, обновление статистики, immutable результаты, HP/healing/Max HP, однократную смерть, отсутствие возрождения, ошибочные входы/RNG и атомарность неудачных операций. - `npm test`: 176 Vitest-тестов прошли (86 Combat Core + 90 Character Stats), также прошли 6 прежних Node-тестов прототипа; пропусков нет.
- `npm run typecheck` и `npm run build`: успешны. Сохранено прежнее информационное предупреждение Vite о размере bundle; игровых импортов нового ядра пока нет.
- `npm run test:e2e`: финальный запуск прошёл, включая движение, бой, опыт, улучшения, смерть/рестарт, мобильное управление и проверку пула 240 врагов. Ошибок JavaScript нет.
- Сначала браузерному тесту не хватало работающего dev-сервера; после запуска один прогон остановился из-за неожиданного состояния `paused` при подборе опыта. Диагностическая копия с логированием клавиатуры/видимости и затем повторный **неизменённый** тест прошли. Причина той паузы не установлена; существующий тест и игровая логика не изменялись.

### Интеграция Task 02

Эти правила принадлежат оружейному слою; `resolveAttack` остаётся универсальным. [Подробнее](WEAPON_ATTACKS.md).
